# AI Agent 上线前必须过的 5 道关：一个真实项目的工程手记

去年到今年，我写了十来个 AI Agent 项目：个人理财助手、科研工作台、客服机器人、内容发布引擎。上线过、翻过车、也修过别人留下的坑。

一开始我以为难点在模型。后来发现不是——**模型早就够用了，真正让人栽跟头的是模型之外的那圈工程**。

这篇文章不讲 Prompt 技巧，也不讲框架选型。我拆 5 个真实踩过的坑，每个都能让一个看起来很好的 Agent 在真实场景里崩掉。

## 第一关：工具调用的「权限悬崖」

Agent 和聊天机器人的分水岭是**它会动手**。一旦会动手，安全模型就完全变了。

我做过一个内容发布 Agent，功能是「写稿 → 排版 → 发到平台」。开发阶段一切正常。上线第二天出事：一次模型幻觉让它把同一篇文章连发了三遍，第三遍还把标题里的「草稿」去掉了——直接变成了正式发布。

问题不在模型，在我没设计权限边界。正确的做法是**给工具分级，而不是给 Agent 授权**：

```python
# 错误做法：Agent 有发布权限，它想发就发
tools = [write_article, format_article, publish_to_platform]

# 正确做法：按"可逆性"分三级
tools = [
    read_sources,        # L0 只读：随便调，无副作用
    write_draft,         # L1 可逆：写草稿，随时能删
    publish_to_platform, # L2 不可逆：必须人工确认
]
```

判断标准只有一条：**这个操作能不能一键撤回？**

- 能撤回的（写草稿、建临时文件、发测试消息）→ Agent 自主执行
- 不能撤回的（群发消息、支付、删除数据、公开发布）→ 强制人工确认

我现在的默认配置是：**所有 L2 操作都要一个显式的确认闸**。哪怕这会降低「自动化感」，也比半夜被用户投诉强。

## 第二关：上下文不是越多越好，是越准越好

刚开始做 Agent 时，我的本能是把所有信息都塞进上下文：用户资料、历史对话、知识库全文、工具说明。结果两个问题同时出现：

1. 成本飙升（每次调用吃掉几万 token）
2. 效果反而变差——模型在多步推理中**丢掉了关键信息**

这不是模型变小了。而是**噪音淹没了信号**。上下文里塞 50 条历史消息，模型要找出「哪 3 条和当前问题有关」；塞 5 条精准的，它反而推理得更稳。

我后来固化成三条规则：

**规则一：分层检索，不要一锅端。**
长对话场景先按时间窗口截断，再按相关性重排。不要直接把全部历史丢进去。

**规则二：给上下文标来源和时效。**
「这是 3 天前的用户原话」和「这是系统配置」对模型的权重应该完全不同。加上时间戳和信息类型标签，多步推理的错误率明显下降。

**规则三：宁可让 Agent 主动查，不要提前喂。**
如果一个信息只在 30% 的对话里用到，别放系统提示词里。让 Agent 需要时自己调工具查——这样既省 token，又避免它拿过期信息做决策。

## 第三关：多步推理的「中间态丢失」

这是 Agent 最难调的一类 bug：**单步都对，连起来就错**。

举个真实的例子。一个科研助手 Agent 的流程是：读论文 → 提取方法 → 设计实验 → 写报告。测试时每一步单独看都没问题，但完整跑一遍，报告里的实验设计和论文里的方法对不上。

排查了很久才定位：**第二步提取的方法，在第三步被「重新总结」了一遍，细节丢了**。

根因是我让每一步都「输出自然语言」，而不是结构化数据。自然语言经过一次转述就会失真，多步下来误差累积。

修复方式很简单：**关键中间结果必须结构化**。

```python
# 错误：每步输出自然语言，信息在转述中流失
def step2_extract(paper_text) -> str:
    return llm(f"提取这篇论文的方法：{paper_text}")

def step3_design(method_summary: str) -> str:
    return llm(f"基于这个方法设计实验：{method_summary}")

# 正确：中间态是结构化对象，字段明确、可校验
@dataclass
class MethodSpec:
    name: str
    components: list[str]
    parameters: dict[str, float]
    assumptions: list[str]

def step2_extract(paper_text) -> MethodSpec:
    return llm_structured(f"提取论文方法", schema=MethodSpec)

def step3_design(method: MethodSpec) -> ExperimentSpec:
    # 直接拿到结构化字段，不存在"总结丢细节"
    return llm_structured(f"设计实验验证 {method.name}", schema=ExperimentSpec)
```

这个改动让整条链路的准确率提升非常明显。**Agent 工程里，结构化的中间态就是防腐层。**

## 第四关：可观测性——你根本不知道它错在哪

这是我最想强调的一点。

Agent 出问题时，普通日志完全不够用。你看到的是「最后输出不对」，但**错在哪一步、模型当时看到了什么、工具返回了什么**，全都没有。

我后来的做法是**给每一次 Agent 运行都存一份可回放的执行轨迹**：

```python
@dataclass
class Trace:
    step_id: int
    type: str           # thought | tool_call | tool_result | final
    input: dict         # 这一步的完整输入（含当时的上下文）
    output: dict        # 这一步的实际输出
    model: str          # 用了哪个模型
    tokens: int         # 这步花了多少 token
    duration_ms: int
    error: str | None
```

存这份轨迹的成本很低（就是结构化日志），但价值极高：

- **出问题能定位**：是模型推理错了，还是工具返回了垃圾？
- **能对比改版效果**：同一个 case 改 prompt 前后，哪一步变了
- **能发现隐性成本**：哪一步在疯狂重试，token 都烧在哪

我现在的习惯是：**任何一个 Agent 上线前，先确认它的每一步都能被单独拿出来看。** 做不到这一点，就不要上线——因为你连它为什么错都不知道，只能瞎调。

## 第五关：失败路径要显式设计，不能靠 try/except 兜

早期我写 Agent 的失败处理就是包一层异常：

```python
try:
    result = agent.run(task)
except Exception as e:
    logger.error(e)
    return "抱歉，出了点问题"
```

这在 demo 里够用，在生产里是灾难。因为**Agent 的失败不是二元的**：

- 模型返回了格式不对的 JSON（可重试）
- 工具超时（可重试，但要退避）
- 工具返回了明确的业务错误（不该重试，要换路径）
- 模型陷入了循环（要打断并降级）
- 权限不足（要立即停，别浪费 token）

这些情况需要**不同的处理策略**，而不是一个统一的兜底。

我现在的 Agent 都会显式定义失败分类和处理矩阵：

| 失败类型 | 处理策略 | 是否通知人 |
|---|---|---|
| 格式错误 | 重试（最多 2 次，附带错误信息） | 否 |
| 工具超时 | 指数退避重试 | 否 |
| 业务错误 | 换备选路径 | 视严重度 |
| 死循环 | 打断 + 降级为简单模式 | 是 |
| 权限拒绝 | 立即停止 | 是 |

**关键是给每种失败一个明确的出口，而不是让它们都掉进同一个 except。**

## 写在最后

上面这 5 关，没有一条是关于「怎么让模型更聪明」的。因为：

> **模型能力决定 Agent 的上限，工程约束决定它的下限。**

而用户感知到的，永远是下限。

一个 Agent 哪怕模型再强，只要有一次越权操作、一次上下文污染、一次中间态丢失，用户就不敢再用了。反过来，一个能力中等的 Agent，只要权限清晰、有可回放轨迹、失败路径明确，用户会信任它、依赖它。

所以如果你正在做 Agent 项目，我的建议是：**先把这 5 关过一遍，再回头优化模型和 prompt。** 顺序反了，后面全是白工。
