# MCP 落地一年，我总结了 6 个没人告诉你的工程真相

去年 MCP（Model Context Protocol）刚火的时候，我花了一个周末把常用的十几个工具全接了进去。当时的想法很朴素：Agent 能调的工具越多，能干的活就越多。

一年过去，我维护着一个收录了 4400+ 个 MCP 服务器的目录，自己也在多个生产项目里用 MCP 接工具。回头看，当初那个想法只对了一半。

**工具数量决定上限，但工程细节决定可用性。**

这篇文章不重复官方文档里的「什么是 MCP」，只讲真实落地时踩出来的 6 个工程真相。

## 真相一：工具描述的质量，比工具本身重要 10 倍

MCP 的核心交互是：模型看到工具的**名称、描述、参数 schema**，然后决定调哪个、传什么参数。

这意味着——**描述就是模型的说明书**。而大多数人写描述时，默认「模型应该懂」。

我见过最典型的一个坑。某工具描述是：

```text
name: query_data
description: 查询数据
parameters: { sql: string }
```

看起来很清晰对吧？结果模型经常拿它去做各种奇怪的查询，包括该走别的工具的写操作。

改成这样之后，调错率立刻降下来：

```text
name: query_data_readonly
description: |
  在只读副本上执行 SELECT 查询。仅支持 SELECT 语句，不支持 INSERT/UPDATE/DELETE。
  表结构：users(id, name, email, created_at)；orders(id, user_id, amount, status)。
  单次查询返回不超过 100 行。需要聚合分析时优先使用 aggregate_stats 工具。
parameters: { sql: string }
```

四个关键信息：**只读边界、表结构、返回限制、相关工具的指引**。

这是 MCP 与写传统 API 文档最大的不同：API 文档给人看，人出错了会自己 debug；工具描述给模型看，模型出错了只会更离谱地猜。

## 真相二：参数 schema 要「防呆」，不要「灵活」

传统 API 设计追求灵活性，MCP 工具设计恰恰相反——**要尽可能减少模型的选择空间**。

我最早做时间参数时给的是自由字符串：

```json
{ "time_range": { "type": "string", "description": "时间范围" } }
```

模型会传什么？`"最近一周"`、`"last week"`、`"2026-10-01~2026-10-07"`、`"过去7天"`——全都出现过。然后我的解析代码要兜住所有这些格式。

后来改成枚举 + 结构化参数：

```json
{
  "time_range": { "type": "string", "enum": ["today", "last_7d", "last_30d", "custom"] },
  "custom_start": { "type": "string", "description": "ISO 8601，仅 time_range=custom 时必填" },
  "custom_end": { "type": "string", "description": "ISO 8601，仅 time_range=custom 时必填" }
}
```

解析代码从 40 行降到 8 行，调用成功率从「经常要重试」变成「一次就对」。

**防呆设计的三个原则：**

1. 能用枚举就别用自由文本
2. 参数之间有依赖关系时，在 description 里写清楚条件（「仅当 X=Y 时必填」）
3. 有默认值的参数，说明默认行为是什么

## 真相三：错误信息是给模型的「观察结果」，不是给用户的「报错」

这是我最晚才想明白的一点。

普通程序的错误信息写给开发者看：`TypeError: NoneType object has no attribute 'split'`——开发者一看就懂。

但 MCP 工具返回的错误，**首要读者是模型**。模型要根据错误信息决定下一步：是重试、换参数、还是换工具。

错误的做法：

```python
return {"error": "Invalid parameter"}
```

模型拿到这个只能瞎猜。正确的做法：

```python
return {
    "error": "user_id 无效：未找到 ID 为 'abc123' 的用户。",
    "hint": "user_id 必须是 32 位十六进制字符串，例如 'a1b2c3...'。你可以先用 search_users 工具按邮箱查找用户 ID。",
    "retryable": False
}
```

带上**三件套**：错在哪、正确格式是什么、下一步可以调什么工具。

我改完错误信息之后，多步任务的失败率有明显下降——因为模型不再在错误的分支上反复重试了。它知道该换工具而不是重试。

## 真相四：工具不是越多越好，「工具路由」才是关键

上下文窗口是稀缺资源。每个工具的描述 + schema 都要占 token。接了 50 个工具之后，每次对话光工具定义就吃掉几千 token，而且模型的选择准确率会下降——选项太多，它反而容易挑错。

我现在的做法是**分层暴露**：

- **核心层**（5-8 个工具）：每次对话都可用。读取类、搜索类、最常用的操作
- **扩展层**（按需加载）：通过一个「查找工具」的元工具暴露。模型需要什么能力，先搜工具，再动态挂载
- **管理工具本身**：把「列出我有哪些工具」「加载某组工具」也做成工具

听起来有点绕，但效果很直接：默认上下文的工具开销从 8000 token 降到 1500 token，而模型知道自己「随时能拿到更多的工具」，不会因为工具不够而摆烂。

## 真相五：幂等性设计——MCP 世界的「安全带」

模型会重试。真的会。

网络抖动、超时、它自己觉得「刚才那次可能没成功」——任何原因都可能让它把同一个调用再发一遍。

如果你的工具不幂等，重复调用就会出事故。我最初做「发送通知」工具时没加幂等，结果模型一次对话里给同一个用户发了三条一样的通知。

现在所有有副作用的工具都会带幂等键：

```python
@tool
def send_notification(user_id: str, message: str, idempotency_key: str):
    """发送通知。idempotency_key 用于防止重复发送：
    同一 key 的调用只会实际发送一次，重复调用直接返回首次结果。"""
    if seen(idempotency_key):
        return cached_result(idempotency_key)
    ...
```

schema 里把 `idempotency_key` 设为必填，描述里写清楚「同一次任务的重复调用请使用相同的 key」。

小改动，但它把「模型行为不可控」的一大类风险直接消掉了。

## 真相六：可观测性要从第一天就有

MCP 工具的调用链路长：模型决策 → 工具调用 → 外部系统 → 返回 → 模型再决策。

出问题时，你面对的是一个黑盒：用户说「明明数据是有的，它就是查不到」，而你要定位是模型选错工具了、参数传错了、还是下游系统挂了。

没有可观测性，这个定位过程就是猜。

我的最小可观测配置：**每一次工具调用记录五元组**。

```python
{
  "tool": "query_data_readonly",
  "params": {"sql": "SELECT ...", "limit": 100},   # 完整参数
  "duration_ms": 342,
  "result_size": 2048,                              # 返回大小
  "outcome": "success | error | timeout",
  "session_id": "...",                              # 串起整个对话
}
```

就这些，存 JSONL 就行，不需要上什么重型系统。

它能回答 90% 的排障问题：模型是不是在反复调同一个工具（参数传错没被发现）？某个工具的失败率是不是异常高？这次对话总共调了多少次工具（成本分析）？

## 写在最后

MCP 这一年，最大的体会是：

> **工具协议标准化了，但工具质量永远不会标准化。**

协议解决的是「怎么连」，而用户感知到的是「连上之后好不好用」——好不好用，取决于上面这 6 条里的每一条工程细节。

我的建议是：如果你正在给 Agent 接工具，**先精写 5 个工具的描述和错误处理，再考虑接入第 6 个。** 质量永远优先于数量。
